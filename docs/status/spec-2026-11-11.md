## Rollback gate

The old 277d2d3 image is **not** a rollback path. Against the migrated database its startup `db push` refuses (it would drop newer tables), so it fails to start; it does not corrupt data. This was rehearsed with Prisma 7.10; the old image used Prisma 6, which has the same refusal without `--accept-data-loss`.

**Rollback** means: revert to an earlier secure revision of this series (tested: an older secure revision starts on the newest schema), or restore from a backup (drill tested). The unauthenticated baseline is never a rollback target.

**IF-CR01: invite revocation races session issuance.**
- **Reproduced first** on real PostgreSQL at `c0cef09`: claim, then revoke, then create the session left that session `active` (`db-invite-revocation-race` test 1).
- **Fix:** `enroll()` locks the invite row (`FOR UPDATE`), re-checks used, revoked and expiry with the clock read under the lock, then creates the session and marks the invite used, all in **one transaction**. `revoke()` takes the same lock. Session lookup also re-checks an invite-based session's invite.
- **Tests:** 5 tests on two real connections cover:
  - the reported interleaving;
  - a revocation that races an enrollment paused between claim and session;
  - a session-write failure, which rolls back with the invite still usable, and a retry that enrolls once;
  - simultaneous enrollments (at most one);
  - the expiry boundary under the lock.
- **Mutation checks:** removing the lookup re-check fails test 1. Removing the enrollment lock together with the re-check fails tests 1, 2 and 4. Moving the claim outside the transaction fails 3 tests. Skipping the expiry check fails 1. The revoke-side lock alone is redundant (PostgreSQL serializes revoke's UPDATE behind the enrollment lock) but is kept for clarity.
- **Invites remain off** (`ROLE_INVITES`).

**IF-CR02: storage states and duplicate receipts (PR #22), confirmed:**
- **Storage states:**
  - not configured: 409 `MEDIA_STORE_NOT_CONFIGURED`;
  - full: 507 `MEDIA_STORE_FULL`;
  - unavailable, refused, or a throw: 503 `MEDIA_STORE_WRITE_FAILED`.
  - In each case: no asset, no lineage, item unchanged (approval kept), and a retry after recovery succeeds once (`db-storage-failures`).
- **Receipts:** checked under a transaction advisory lock on (campaign, payment reference), counting only receipts that aren't reversed. Corrections stay possible after a reversal, and void and reverse history is kept (`db-measurement`).

**IF-CR03: media acceptance, closed for the private-export scope:**

- **Not a finished voiced or captioned video:** the output is described as silent, with captions not burned in. Speech, music and burned-in captions are later scope.

**IF-R3, media rules:**
- **PNG:** every chunk is walked with its CRC checked; IHDR must come first, a non-empty IDAT is required, IEND must come last with nothing after it, and there is a pixel limit (50 M).
- **JPEG:** frame header, scan data and end marker are required.

**IF-R4, recovery rules:**
- A takeover sets a fresh 5-minute lease.
- Each step's money and state change in one transaction that locks the job row and proceeds only while the recoverer still owns it.
- The final job update is fenced the same way, and a recoverer that lost the job stops.
